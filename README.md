# MCLanP2P (Python)

把 Minecraft 联机流量走 P2P 隧道。**服务端和客户端都是纯 Python 标准库**，
不需要 pip 装任何东西，也不需要 .NET SDK / 编译器。

```
server/server.py   信令服务端（纯标准库 asyncio）
client/            tkinter 图形客户端
```

> 测试套件（`test_*.py`、`check_sources.py`、`local_test.py`、`bench_punch.py`）
> 属于本地开发工具，**不随仓库分发**——clone 下来的是可直接运行的成品。

---

## 快速开始

### 客户端（Windows / macOS / Linux）

日常用，直接跑：

```bash
cd client && python main.py        # Windows 双击 client/run.bat
```

想打包成单个 exe（Windows，便于发给朋友）：

```bash
python build.py                    # 或双击 build_client.bat
# -> dist/MCLanP2P.exe
```

`--onefile` 模式会把 `settings.json` 存在 exe 旁边，配置不会丢。

### 服务端（Linux 服务器）

```bash
sudo ./deploy-server.sh            # 默认 5000 端口
sudo ./deploy-server.sh 8080       # 自定义端口
```

服务端**不打包**，就以 Python 脚本形式跑。原因：

- Linux 自带 python3，本来就不需要安装任何东西
- 不需要构建工具链，也就没有 glibc 兼容性问题
- 部署就是拷一个文件，改一行配置立刻生效，不用重新构建

脚本会装到 `/opt/mc-p2p/server.py` 并配好 systemd + logrotate。

或者临时跑一下：

```bash
PORT=5000 python3 server/server.py
```

查看日志：

```bash
sudo journalctl -u mc-p2p -f        # 进程日志
sudo tail -f /var/log/mc-p2p.log    # 业务日志
```

**云服务器还要在厂商安全组放行 TCP 端口**（ufw/firewalld 只是本机防火墙）。

## 提交到 GitHub

```bash
python push_github.py            # 或双击 推送到GitHub.bat
```

默认推到 `https://github.com/radix-angelicae/MCLAN`，标签 `mclanp2p-simple`。

**只提交源码**：不运行 `build.py`、不生成 `dist/`、不创建 GitHub Release。
提交信息带 `[skip ci]`，避免一次"保存一下"就触发远端构建。需要发布二进制包时
另外手动执行 `python build.py`。

首次运行会自动 `git init`、生成 `.gitignore`（排除 `dist/ build/ __pycache__/
.device_id settings.json`）、配置 remote 和提交身份。重复运行安全：工作区没改动
就不会产生空提交，标签会跟着新提交往前走。

常用参数：

| 参数 | 作用 |
|---|---|
| `--proxy http://127.0.0.1:10808` | 指定代理（默认就是 10808） |
| `--no-proxy` | 不走代理，并清掉本仓库已设的代理 |
| `--ssh` | 改走 `git@github.com:radix-angelicae/MCLAN.git`（会自动关掉代理） |
| `--tag 名字` / `--no-tag` | 换标签 / 不打标签 |
| `--no-push` | 只提交到本地 |
| `--dry-run` | 只预演，不改动任何东西 |

代理写进的是**本仓库**的配置（`git config`，非 `--global`），所以用 `git config --list`
能看到、用 `--no-proxy` 能撤销，不会悄悄影响这台机器上别的仓库。

HTTPS 直连 GitHub 被复位（`Recv failure: Connection was reset`）时脚本会给出分类诊断，
并把"走代理"排在第一条——那是网络层失败，不是没登录，也不会有登录弹窗。

**强推**：脚本默认带 `--force-with-lease`（不是裸 `--force`）。这个仓库远端只放一个
LICENSE，本地这份才是权威来源。lease 只在"远端出现了我们 fetch 时没见过的提交"时拒绝，
也就是另一台机器在我们运行期间推过东西——那种情况下不会在不知情时覆盖。
`--force` 无条件强推，`--no-force` 只在能快进时推。

## 配置文件放在哪

配置**不再**存在程序所在目录，而是存到系统给每个用户预留的位置，
这样程序放在哪个文件夹、甚至挪到 U 盘都不影响，也避免了放在
Program Files 时没权限写入的问题：

| 系统 | 位置 |
|---|---|
| Windows | `%APPDATA%\MCLanP2P\settings.json` |
| macOS | `~/Library/Application Support/MCLanP2P/settings.json` |
| Linux | `~/.config/mclanp2p/settings.json`（尊重 `$XDG_CONFIG_HOME`） |

日志文件在配置目录下的 `logs/`。点界面上的「打开配置目录」可直接跳过去，
启动日志里也会打印实际路径。

**旧配置会自动迁移**：升级后首次启动时，会把程序目录里旧的
`settings.json` 和 `.device_id` 搬到新位置，昵称、服务器地址、设备 ID 都不会丢。

保存的字段：服务器地址、昵称、手动公网 IP、连接模式、MC 端口、UDP 打洞端口、
本地代理端口、世界名、人数上限。全部实时保存（改动即写，崩溃也不丢）。

设置 `MCLANP2P_HOME` 可强制指定目录（测试、多开时使用）。
上述位置都不可写时，才回退到程序目录。

## 房间人数上限

房主建房时在「人数上限」框里填（2-64，默认 10）。服务端会校验并在人满时
拒绝新成员，返回中文提示「房间已满 [ROOM_FULL]」。

超出范围的值会被自动收敛：填 1 变 2，填 99999 变 64。**注意上限由房主决定**，
其他人的输入框只在自己建房时生效。

房间列表现在只显示「世界名（房主 x，2/10 人）」，不再显示四位房间代码——
代码仍随行保存，点「加入」照样能进。

**成员列表会显示每个人的 NAT 等级**，例如
`小明 [房主]  22 ms  ·  对称·递增（可预测） · 入站宽松`。

这是给"为什么我连不上"这类问题准备的：绝大多数连不上的情况，根源是某一个人的
网络，而以前唯一的排查方式是让那个人去翻自己的日志念给你听。现在房主一眼就能
看出问题在自己这边、对端那边，还是这一对组合本身。

标签刻意区分两种对称型：`对称·递增（可预测）` 和 `对称·随机（难）` 都是 NAT4，
但前者能靠端口预测打通、后者基本只能走中转——只报"NAT4"等于没说。后面的"入站
宽松/中等/严格"来自 RFC 5780 的过滤行为，严格意味着那一端必须先开口，否则对端
的包进不来。

## 链路自愈与房间生命周期

**直连断了会自动重建。** UDP 打出的"洞"不是连接，NAT 映射超时或对方重启时
不会有任何报错——对端只是不再应答。以前客户端会一直往死隧道里发数据，界面
还显示"运行中"，游戏却卡住不动。现在有一条看门狗：20 秒收不到任何包就判定
链路死亡，然后按模式处理——`direct` 重新打洞，`auto` 改用服务器中转。

判定死亡时会主动断开本地的 Minecraft 连接，让玩家看到"连接中断"并重连到新链路，
而不是对着一个假装在跑的世界干等。

**房主离开即解散房间。** 拓扑是星型的：所有客人连向房主，世界也跑在房主机器上。
以前房主离开只是从成员表里被摘掉，房间变成"孤儿"——客人还待在里面却无人可连，
界面仍显示一个已经不存在的房主，新人还能从列表里看到并加入这个死房间。
现在房主一走，房间立即解散，所有客人收到「房主已离开，房间解散」。

注意：房主**断线自动重连**时会恢复房间，这是有意的（网络闪断不该让整局结束）。
只有房主真的不回来（关掉程序、重连关闭）才会解散。

## 内置 STUN（服务端自带，无需额外部署）

`deploy-server.sh` 启动的服务端进程**同时提供 STUN 服务**（默认 UDP 3478 + 3479），
客户端连上信令后会自动优先使用它，不再依赖第三方公共 STUN。

为什么重要：公共 STUN 是"尽力而为"的——会被墙、被限速、被运营商屏蔽
（`stun.l.google.com` 在国内不可达，`stun.qq.com` 已有多方报告不再响应）。
一旦探测失败，客户端会退化为局域网地址，**直连就彻底不可能了**，只能走中转。
也就是说：以前直连能否成功，有一部分是被第三方服务器的上线率决定的。

自带 STUN 是你自己的 VPS，**一定可达**（前提是安全组放行）。

**两个端口是故意的**：判定 NAT 类型需要向两个"不同目标"各发一次请求，
单 IP 的 VPS 只能通过换端口来提供两个目标。第二个端口不通也没关系——
只是测不出 NAT 类型，公网地址照常能拿到。

两个端口在**同一个 IP** 上，这有个诚实的边界：能测出"按目标端口递增分配"
的 NAT（两次映射不同 → 对称型 + 步长），但测不出"按目标 IP 分配"的 NAT——
那种 NAT 对同一 IP 的两个端口给出同一个映射，和锥型完全无法区分，
只能乐观地判为锥型（日志会打印 `[NAT] ... type may be optimistic`）。
想区分就再给一个 IP 上的 STUN（客户端会继续往下问，凑够 2 个应答为止，
6 秒预算内）。

### 服务端需要开放的端口

| 端口 | 协议 | 说明 |
|---|---|---|
| 5000 | TCP | 信令 + 数据（可改） |
| 3478 | UDP | 内置 STUN（主） |
| 3479 | UDP | 内置 STUN（辅助，用于 NAT 类型判定） |

部署脚本会自动配 ufw / firewalld / iptables，**云安全组必须手动再开一遍**。
UDP 没放行的话日志会出现 `STUN failed`，此时直连不可用（中转仍可用）。

不想跑 STUN：`STUN_PORT=0 ./deploy-server.sh`。

客户端探测有 6 秒总预算，避免 UDP 被封时把整个列表走一遍（16 个 × 3 秒 = 48 秒卡顿）。
在这 6 秒里它按顺序一直问下去，**直到凑够 2 个应答**——挑两个服务器再固定
下来是不够的：内置 STUN 通、公共 STUN 不通（国内常见）时，两个里挂掉一个
就只剩 1 个样本，NAT 类型直接变成 unknown，端口预测也跟着关掉。

**客户端会先等服务端把 STUN 地址送过来再开始探测**（最多等 3 秒）。这一步
不能省：`register` 和 `publish_offer` 是连着发出去的，但服务端的回复要等一个
完整的 RTT 才到，不等的话探测必然抢在前面，问的是公共列表而不是内置 STUN——
也就是内置 STUN 一次都没被问过。如果 3 秒内没等到（比如老版本服务端），
客户端会先发布一次、之后在拿到地址或建房/加人时**补发**一次；已经拿到
公网地址的则不会重探——对称型 NAT 上多探一次就会多占一个映射槽位，把对端正
在瞄准的那个洞挤歪。

## 安全说明

**先说实话：这套东西的定位是"朋友之间联机"，不是安全产品。**

已做的加固：

| 项 | 状态 |
|---|---|
| 房间密码 | 支持（创建时可选，服务端存 salted hash 而非明文） |
| 加入限流 | 每连接 30 秒内 8 次 **+ 每源 IP 30 秒内 30 次**（房间码只有约 100 万种组合，不限流可被枚举） |
| register 防刷新 | 一条连接只能 register 一次；限流按**源 IP**计数，重发 register 换 clientId 不再重置配额 |
| 帧长上限 | 单条消息 8MB，控制帧 125B，防 OOM |
| RSV / Sec-WebSocket-Accept 校验 | 已校验，防错流与假冒握手 |

**装在反向代理后面时必读：**

限流按"客户端来源地址"计数。套了 nginx 之后，服务端看到的每个连接都来自
nginx 自己，于是**所有玩家共用一个配额**——一个房间的正常重连就能把互不相干
的人锁在门外。两种解法，选一个：

```bash
# A. 让服务端认 X-Forwarded-For，并只信任你这台代理
TRUSTED_PROXIES=127.0.0.1 ./deploy-server.sh

# B. 直接关掉按来源地址的限额（每连接的 8 次/30 秒仍然生效）
MAX_JOIN_PER_IP=0 ./deploy-server.sh
```

注意 `TRUSTED_PROXIES` 只能填你自己的代理地址。无条件信任
`X-Forwarded-For` 比不认它更糟——那是客户端可以随便写的请求头，伪造一个
新地址就等于换一份新配额。填了值之后，格式不合法的头会被丢弃并退回真实
socket 地址。

**仍未解决的**：

- **全程明文**：`ws://` 而非 `wss://`。relay 模式下服务器能看到全部 MC 流量。
  要加密得部署 TLS 反代（nginx + Let's Encrypt），属于部署层改动。
- **直连侧无加密无鉴权**：UDP 隧道只比对源 IP，能伪造源地址就能注入数据。
  AEAD（`ChaCha20-Poly1305`）需要一次密钥协商，尚未实现。
- **房间密码不是强认证**：8 次/30 秒的限流下，6 位数字密码仍可爆破。
  密码请设得长一些。
- **还没有 TCP 同时打开（simultaneous open）旁路**：绑定本地端口后 TCP 打洞是
  可行的，且不少 NAT 的 TCP 端口分配比 UDP 更好预测，NAT4 下常是唯一能通的路。
  本版未实现，因此这类网络目前只能走中转。
**IPv6 旁路**：本版会收集本机全球 IPv6 地址并发布，排在所有候选之前，链路-local
（`fe80::`）不参与。源地址用"问内核它会选哪个"的方式取（`connect()` 到公共 v6
地址再读 `getsockname`），而不是解析主机名——大部分 Linux 主机的 hostname 只
解析到 `::1`，那样 v6 列表会直接为空。

但"IPv6 不过 NAT"**只对了一半**：家宽路由普遍放行 v6 出向、阻断 v6 入向。没有
NAT 不等于没有防火墙。所以 v6 尝试只给 3 秒（而不是整个打洞预算），失败立刻
回落到 v4，不会让用户干等。本项目没有实现 IPv6 打洞，因此"有 v6 但收不到包"
这一类最终仍走 v4 路径。

## 直连的已知限制

**同一 NAT 后的两个 peer**（两人在同一个宿舍/公司网）在直连模式下无法区分：
hub 按源地址路由，两个 peer 的公网 IP 相同，冲突的包会被丢弃。这种情况请用
`relay` 模式。

**端口预测只是启发式。** 对称型 NAT 能否打洞取决于对方的端口分配算法，
**也取决于能问到几个 STUN 目标**（实测，用模拟器跑的）：

| NAT 分配行为 | 可用 STUN | 结果 |
|---|---|---|
| 锥型（端口固定） | 任意 | 直连成功 |
| 按目标 IP 分配 | 两个不同 IP 的 STUN | 直连成功 |
| 按目标 IP 分配 | 仅内置 STUN（同一 IP 两个端口） | **失败**：两个端口拿到同一映射，判为锥型，预测不启用 |
| 按目标端口顺序递增（严格 NAT4） | ≥1 个 IP | 直连成功 |
| 按目标端口递增 + 1~3 条背景 UDP 流 | ≥1 个 IP | 实测 5/5 成功 |
| 随机分配（Linux conntrack、多数家用路由、手机热点） | 任意 | 走随机碰撞（生日攻击）：多 socket 开映射 + 每轮新猜端口 |

顺序递增这一类比原先估计的容忍得多：喷射是单向的、从 `端口+Δ` 开始一路往前
走，只要对方的分配是单调的，背景流多占掉几个槽位通常仍在覆盖范围内（实测带
1~3 条背景流仍 5/5 成功）。所以**判成对称型时不要提前放弃**，先打一次看结果。

第三行不是 bug，是信息论边界：只有一个 IP 可问时，"对所有目标同一映射"和
"对每个目标 IP 一个映射"产生的观测完全相同。真要在这种部署下打通，
得再有一个 IP 上的 STUN 可用。

随机分配的那一行不再是"只能走中转"：预测没有意义，但**碰撞**有。一端开上百个映射当靶子，
另一端每轮重新随机猜端口，命中率按 `1-(1-K/65535)^N` 上升。代价是包量与时间，所以它排在
窗口扫描之后。

喷射有上限并带随机扰动——顺序固定、无上限的喷射在地址过期时等同于扫描无辜
主机。已确认对称型用 50 个端口的窗口（与 EasyTier 同量级），未测出的 NAT
用较窄的 24 个，因为对它我们本来就在猜。

## 三条旁路（优先于任何打洞）

按确定性和代价排序，能走就走：

| 旁路 | 状态 | 说明 |
|---|---|---|
| IPv6 | 已实现 | 排在所有候选之前；**但"有 v6"不等于"能收包"**，见下 |
| UPnP / NAT-PMP | 已实现 | 路由器批一个公网端口，NAT 问题不复存在 |
| TCP 同时打开 | 已实现 | 绑定本地端口互拨；是否保留端口由服务端实测。UDP 实打实失败过一轮就试 |
| 中转 | 已实现 | 最后的保底 |

## 先走正门：UPnP / NAT-PMP

所有打洞技巧都是**概率**；端口映射是**事实**。只要路由器同意把某个公网端口
转发给我们，我们就真的有了公网端口，对端直接连上来即可，NAT 问题不复存在——
这是收益最高、副作用最小的一条路，所以**先试它**。

客户端连接后会在后台做一次 SSDP 发现 + SOAP 映射（UDP 30000），成功就用这个
地址重新发布，并每 240 秒续约一次；断开时主动归还端口。

路由器没开 UPnP 是常态（有些厂商默认关闭），此时静默回退到打洞，日志里会写
一行 `[UPnP] no mapping available (normal: UPnP off or filtered)`。**这不是错误。**

不想用（比如不信任路由器）：不装 `upnp` 模块或让它不可用即可，其余功能不受
影响。

## NAT4 不是一种 NAT，是一条光谱

把"对称型 = 打不穿"当成结论，是 NAT4 直连率低的根本原因。真正的问题只有
一个：**对端不知道我"这一次"会被分到哪个公网端口**。而这件事能不能猜到，
取决于 NAT 怎么分配端口——大部分家用路由是**顺序**分配的，也就是可预测的；
只有一部分是真随机。

所以本版在原来的 `cone / symmetric` 之外，多问了一个问题来判断到底属于哪档：

```
p1 = 探测(服务器A, 端口1)
p2 = 探测(服务器B, 端口1)      // 同一端口、换服务器
p3 = 探测(服务器A, 端口2)      // 换一个新端口、问同一个服务器  ← 关键
```

前两次只能说明"映射会随目标变"，**只有第三次能看出下一个映射落在哪**——而
"下一个"正是对端要猜的东西。据此分档：

| 细分类型 | 判定 | 打法 |
|---|---|---|
| `cone` | p1 == p2 | 普通打洞 |
| `sym_easy_inc` | 新端口比 p1/p2 大一点点 | 连续端口窗口预测 |
| `sym_easy_dec` | 新端口比 p1/p2 小一点点 | 同上，方向相反 |
| `sym_hard` | 映射跳得很远，或没有第三个样本 | 随机碰撞（生日攻击） |

**为什么之前打不穿**：旧的预测是**按测得的步长跳跃**扫描。步长测出来是 7，
就打 `+7 +14 +21`；可顺序分配的 NAT 给下一条流的很可能是 `+1`，正好被跳过。
步长只能告诉你**方向**，不能当**步幅**用——现在扫的是连续窗口，一个不漏。

### 多孔打洞

一个端口就是一个靶子。对真随机的 NAT 没有任何可预测性，唯一能做的杠杆就是
**让自己这边的靶子变多**：开 N 个端口，对端随机撞，命中率
`1-(1-N/65535)^k`。所以有了多孔机制——需要时开一批独立映射同时发包，哪个
端口先收到回复，就把它交给正式通道。

**猜了才算数。** 随机碰撞曾经有个记账 bug：每轮抽 600 个端口，但一轮只发得出去
`sockets × 2` 个包（100 个 socket → 200 个）。抽出来的另外 400 个被 `_fresh_ports`
标成"已试过"却**从未发过包**——于是六分之五的端口空间被白白划掉，跑一百来轮就报
"端口池耗尽"，实际只覆盖了六分之一。现在抽取量按真的发得出去的数量封顶，且
**只把真正发出去的端口记进已试集合**（覆盖率报告就是从这个集合算出来的）。

### 策略矩阵

| 我 \ 对方 | cone | easy（可预测） | hard（随机） |
|---|---|---|---|
| cone | 普通打洞 | 我方多孔 + 窗口 | 随机碰撞 |
| easy | 我方多孔 + 窗口 | **双方同时喷** | 我方多孔 + 宽随机喷（**不再放弃**）|
| hard | 我方多孔 + 宽随机喷 | 我方多孔 + 宽随机喷 | 双方都喷（仅两端 eif 时）|

唯一仍然直接转中转的组合是 **hard/hard 且过滤严格（非 eif）**，以及 **apdf 配上一个
不可预测的 NAT**：既没有可瞄的端口，也没有能让回包进来的门，打下去只是白等。

两条硬规则值得单独说：

- **可预测 × 随机不放弃。** 曾经这里返回"无机制"，整个打洞连一个包都没发就转了中转。
  但可预测那一侧的端口**有窗口可扫**，随机只是让**一半**机制失效，不是全部。
- **随机的一侧也要喷。** 曾经"要不要扫窗口"只认 `sym_easy_*`，于是对等端是 `sym_hard`
  时扫描被整个关掉，100 个 socket 对着它**唯一发布的那个端口**发了 8989 个包：

  ```
  [punch] sent 8989 packets to 23653 (anchor measured 2s ago)
  ```

  而它的多孔数组散在 65535 个端口里，一个都没猜。现在不可预测的对端走宽范围随机喷，
  窗口扫描只在对方是 cone 时才关（它的端口不会动，扫了也白扫）。
- **双方都可预测 → 两边都要发**，只是由**过滤更严格**的一方先起（不是 id 大小），
  避免同一毫秒各自开几十个端口。单向发包是开不出洞的。

### 同步起跑

服务端下发 `start_punch` 时附带 `startIn`（一个**相对**延迟），两端各从收到消息
起算、等同样长的时间再开始发包。

用相对量而不是绝对时间戳是刻意的：绝对时间戳要求两端时钟都和服务器对得上，而
"时钟一致"恰恰是 P2P 场景里最不该假设的东西。慢 5 秒的一端要么错过整个重叠
窗口，要么干等一个早已过去的时刻。相对量下，两端起跑之差只等于两者 RTT 之差，
通常几十毫秒，且完全不受时钟影响。

同步只在**第一个公网 IPv4 候选**上等一次：候选是按顺序试的，而 IPv6 / 局域网
候选排在前面，若把等待花在它们身上，轮到公网候选时那个时刻早已过去。锥型对锥型
（cone_to_cone）不等待——没有需要同步的东西。

这个延迟锚定在**收到消息的时刻**（`recv_at + start_in`），而不是"现在起再睡
1.5 秒"。后者看着一样，实则不然：到达公网候选之前，两端各自在 v6/LAN 候选上
花的时间未必相同，于是实际起跑 = 收到 + 各自的前置耗时 + 1.5，前置差多少就错位
多少——一端有 v6/LAN 候选、另一端没有时错位可达 100%。锚定之后只剩 RTT 之差。
已经超过截止时刻就立即开始，不再等一个已经过去的点。

每次收到新的 `start_punch` 会清掉"已等待"标记，否则重建的链路永不再同步。

### 中转是地板，不是天花板

打洞是两个**不断移动的端口分配**之间的碰撞。前两次超时失败，说明的只是那两次，不代表第十次：
对端的锚点会被刷新、手机会换基站、路由会重拨。EasyTier 从不停止尝试，链路打通后原地升级——
这就是它在同一对机器上显示"直连"、而一次定时尝试显示"中转"的主要原因。

所以 auto 模式下，一旦走中转，**后台每分钟再打一次短洞**（8 秒预算），成功就把该 peer 的
通道原地换成直连（游戏不掉线，因为换的是同一个 channel 的 transport，且是在握手完成之后才换）。
direct 模式不启用：它本来就在无限重试，而且用户要的是直连，不是底下垫一条中转。

### 直连失败会退避，不会无限重试

每轮全部候选失败后，间隔按 1→2→4 秒递增；连续 3 轮失败则 direct 模式把该 peer
拉黑 12 秒（提示可切换中转），auto 模式直接转中继——用户需要的是能连上，不是等
一个明知不通的地址。

周期短是有意的：原来是 45 秒退避 + 60 秒拉黑，网络抖一下就要近两分钟才恢复，而
NAT4 恰恰常常在后几轮才打通。短不等于猛——每一轮仍然是一次真实打洞，拉黑仍然是
实实在在的停顿，只是从"分钟级"回到"秒级"。连接成功即清零计数（单孔、多孔、IPv6 三条成功路径都清），黑名单到期自动解除。

黑名单在**每轮循环顶部复查**，而不是进入时查一次——否则"拉黑 60 秒"实际只是
暂停一次，之后又回到 3 秒一次的重试。计数单位也是"公网候选的失败次数"，不是
"每个候选"：局域网和 IPv6 候选失败是常态，让它们推动计数会让
`AUTO_DIRECT_ATTEMPTS=2` 实际只给公网地址一次机会，而 NAT4 常常要靠第二、第三
轮（第一发喷射是在给对端"预热"映射）。

连接中途切换模式会**真的重建链路**：遍历 `self.channels` 逐个 peer 重建（而不是
只看 `target_id`——它在每次 `start_punch` 里被覆盖，只留最后一个，而房主恰恰是有
多条通道的那一侧），关闭通道时连 tunnel 一起关（多孔命中和 IPv6 建立的 tunnel 都
是 `owns_socket=True`，不关就每个模式切换漏一个 UDP 端口），并按新模式重来。

切回直连时会向服务端请求重新协调（`punch_target`），否则两端是各打各的；同时清掉
已过期的同步状态，避免去等一个早已过去的截止时刻。

这个请求带 `force` 标志：对端如果已经有通道（**最常见的情况**——它早就放弃并转了
中继），普通的 `start_punch` 会被直接忽略，于是手动切回直连的一方只能单方面空打。
`force` 会让它重新走一遍打洞。

但 `force` 是 **make-before-break**：旧链路只是被挪到一边继续跑，等新链路真的开始
转发才关掉；新链路没打成就把旧的放回去。被要求重打的一方并没有同意这件事，先拆
后建会让它白白断一次（一轮打洞 + 退避，约 20 秒，Minecraft 连接跟着掉），而这次
尝试很可能还是失败。游戏流量不能因为别人按了一下按钮就停。

失败回退不等整轮结束：第一轮公网打洞失败就把旧链路放回去。等整轮（两轮打洞预算加
退避，约 20 秒）意味着这 20 秒里旧链路不在 `self.channels` 中，玩家重连会被告知
"还没有链路"，剩下的重试在有链路可用的状态下慢慢进行即可。

服务端对这个动作做了限流和按 peer 对的冷却（默认 10 秒）：它让**别人**付出代价，
不能是谁想发就发。

`force` 由客户端显式传（服务端不再硬编码），普通重连请求仍然是非强制的。

同一 peer 的 `start_punch` 到达多次时（双方同时切换会各触发一次，服务端于是发出
两对），已在等待的那一轮会改用新的截止时刻，而不是接着旧时刻睡完。

房主恢复房间时只认**自己拥有**的房间（`ownerId` 匹配）：默认房间名是所有人共享的，
光看名字不是身份。若房主重连时加入了别人的同名房间，会被降级成客人——而本项目的
拓扑里只有房主侧连着本地的 Minecraft，世界会静默跑到别人机器上，且不报错。

轮次计数发生在**真正发起打洞的地方**，而不是候选循环顶部——局域网/IPv6 候选是
`continue` 跳出的，在那里计数会虚高，导致 auto 模式的公网地址只被真正打一次。
只有**公网 IPv4** 才计入：单候选时并不"一定就是公网地址"，`order_candidates`
在只有局域网地址可达时也会产出单元素列表，把一次局域网超时算成打洞失败会白白
消耗重试预算。
纯 IPv6 候选（手动填 `[2001:db8::1]:30000` 这种）例外：它没有别的候选可退，这一
次失败就算一轮，否则会永久卡在"连接中"——那比直接失败更糟。

### 先听见，再回话

这是整套打洞里最重要的一条，也是之前结构上最缺失的一环。

多孔喷射会打开 84 个新映射，而这些端口**从来没有告诉过对端**（信令里只有单个
`p2pAddr`）。如果打完就等，双向必然落空：对端还在打我发布的那一个端口，而我
的收包点已经变成 84 个它毫不知情的随机端口。

所以每个到达的包都被当成**学习机会**而不是"可能的命中"：它的源端口就是对端
NAT 真实创建的映射——正是我们预测不出来的那个数。我们记下来，并**立刻回包**。
这个回包既是从我们这一侧开门，也是在告诉对端"你猜中了"。

实现上有三点：

- 源地址记录后**立刻回 HELLO_ACK**，包括经 hub 转来的包（发布端口通常是第一个
  收到包的地方，对端只知道这个地址）。
- 下一轮**优先回复已学到的地址**，没有学到才继续喷。已知可达的地址比任何猜测
  都值钱。
- reader **不再收到第一个包就退出**。NAT 可能先送来一个无关流的杂包，退出就
  没有第二次机会了——真正的回包晚一点到就永远看不到。

### 随机碰撞里，谁该猜

这一条踩过坑，值得单列：**只有锥型侧需要随机猜，对称侧必须打对端已知端口。**

端口级对称 NAT 的过滤是「按目标」的——发往 X 之后，只接受来自 X 的包。所以
对称侧向随机端口发包打开的映射，永远等不到回包：哪怕对端恰好撞中了那个端口，
包也会被过滤掉，因为我们没往那儿发过。对称侧的任务只是**打开映射**，猜的活
属于锥型侧（它的 NAT 来者不拒）。

实测对照（同一套模拟 NAT，只改"对称侧往哪发"）：

| 策略 | 结果 |
|---|---|
| 双方都喷随机端口 | **0/6** |
| 对称侧打对端已知端口，锥型侧随机扫 | **6/6** |

`both_easy_sym` 的默认参数也从 25 socket / ±20 窗口提到 **100 / ±64**：两条各自
独立递增的分配序列要能对上，25 个样本覆盖不足（实测 1/4，提到 84/±50 后 3/4）。

同理，对锥型对端**不做窗口扫描**：它的端口根本不动，51 个目标里 50 个不可能
应答。窗口扫描只在对方端口确实会移动时才启用。

### 合规开关

多孔喷射从外部看，和"对某个 IP 的端口扫描"没有区别，且确实可能触发运营商
风控。所以：

```bash
DISABLE_SYM_PUNCH=1 python main.py     # 完全关闭对称型喷射，直接走中转
```

单轮包量、全局速率都有硬上限，撞端口用**打乱顺序**而不是顺序遍历（顺序遍历
正是 IDS 判定端口扫描的特征）。关掉之后一切照常，只是 NAT4 直连不再尝试。

限速是**进程级**的：主机同时给 5 个访客打洞也只有一份配额（2000pps），而不是
5×2000——对运营商来说，唯一有意义的数字是从这台机器出去的总量。

这个上限之所以是 2000 而不是原来的 800：一轮喷射是 120 个 socket × 2 包 = 240 包，
按 100ms 一轮算，自然需求就是 2400pps。800 的帽子把轮速压掉一半，也就把 8 秒窗口
内能跑的轮数压掉一半——而窗口宽度和 socket 数量这两个参数本来就是按"覆盖面"算
出来的，轮数减半等于这两个数同时缩水。现在的上限仍然封顶、仍然进程级，只是不再
自己掐自己。

同一个 peer 只会有一个直连循环（**per-peer 单例**）。每次 `start_punch`、每次"链路
中断重建"、每次模式切换都会再起一个循环，而它们共享同一个 channel、各自维护一份
`attempt` 计数——真实日志里出现过 `direct #1` 到 `#10` 同时活着：上千个 UDP socket、
十个独立的失败计数各自触发黑名单、黑名单一到期又撞上另外九个正在打洞的循环。
现在重复的 dispatch 会被拒绝，循环结束时释放名额。

候选列表**每轮重新读取**，不是开局抓一次快照。曾出现过：服务端持续下发新的公网
地址，而客户端整场都在打一个完全不同的旧 IP——新地址一次都没试过，因为循环手里
握的是它到达之前的快照。

`sym_to_cone` 的多孔预算是 8 秒（和 `both_easy` 一致），不是 6 秒：对称侧开一批
端口等锥型侧来扫，而锥型侧通常先烧掉自己的单孔预算才轮到扫描，6 秒时我们这边的
端口已经关了。

### 从一份真实日志里读出来的两件事

一次"直连连不上"的实跑日志里有 `direct #1` 到 `#10` 同时活着，都在打同一个对端。
那不只是浪费：**十个循环各开 100 个 socket，就是一千个映射，而对端扫描的窗口只有
64 个端口**，且锚定在几秒前发布的那一个映射上——绝大多数靶子从来没被瞄过。

1. **per-peer 单例直连循环**（见上）。
2. **`sym_to_cone` 的窗口要比 `both_easy` 宽，而不是共用同一个数。** 这两种场景的
   几何形状相反：`sym_to_cone` 只有一端在动——对称侧开 100 个映射然后不动，锥型侧
   去走一遍，靶子是固定的，窗口越宽命中的越多，没有副作用。`both_easy` 是两端都在
   移动，窗口加宽会把同样的包摊薄，同时自己的源端口还在不断走出对端的射程，所以
   `bench_punch.py` 在那里测出 64 最优、再宽反而下降。

   现在 `sym_to_cone` 是 160（覆盖 100 个 socket + 漂移余量）。漂移是真的存在的：
   从"发布映射"到"开 socket 阵列"之间，这台机器还会产生别的 UDP 流（DNS、STUN
   重试、QUIC），每一条都把下一次分配往后推。

   **速率切片必须相加，不能互相替代。** v9 引入的"按并发均分"曾经算错：共享窗口计数被
   拿去和**单个 attempt 的份额**比较，于是总量被压到"一份份额"而不是"份额之和"。实测
   （真实批量发送）：

   | 并发 | 修复前总 pps | 修复后总 pps | 设计值 |
   |---|---|---|---|
   | 1 | 2467 | 2406 | 2400 |
   | 2 | 1267 | 2415 | 2400 |
   | 4 | 733 | 2435 | 2400 |

   4 个客人并发时修复前每个只有 183pps（设计 600），一轮 200 包要 1.1 秒——8 秒窗口只剩
   7 轮而不是 24 轮。而且这比改之前的单桶（约 2000pps）**更差**，而这次改动存在的理由
   正是星型拓扑。

   现在每个 attempt 持有自己的窗口计数、各自对自己的份额封顶，全局上限由
   `sum(shares) <= pps` 保证（这正是 `MAX_CONCURRENT_PUNCHES` 的作用：
   `600 x 4 = 2400`，刚好不超）。另外**拿不到并发槽位的 attempt 直接跳过**——它不在除数
   里就拿不到份额，却仍会发包，等于把总量推过天花板。

   160 这个数现在有实测支撑了（`bench_punch.py` 新增 `sym_to_cone` 一节，带
   `drift` 参数模拟这段间隔里产生的无关流）：

   | 无关流条数 | ±50 | ±64 | ±100 | ±160 |
   |---|---|---|---|---|
   | 0 | 100% | 100% | 100% | 100% |
   | 60 | 0% | 98% | 100% | 100% |
   | 120 | — | — | 0% | 100% |

   两个结论：**窗口不加宽会在漂移下直接归零**（±50 在 60 条无关流时是 0%），而
   **`sym_to_cone` 里加宽没有代价**——命中率随宽度单调不降，这和 `both_easy`
   里"再宽反而下降"完全相反。所以这里的余量是白拿的。

   又测了"socket 数 vs 窗口"的交换曲线（drift=160，即最恶劣的一档）：

   | socket 数 | ±64 | ±160 | ±220 |
   |---|---|---|---|
   | 60 | 0% | 58% | 100% |
   | 100 | 0% | 58% | 100% |
   | 140 | 0% | 58% | 100% |

   **加 socket 完全没用，只有窗口起作用。** 这条有实际价值：socket 是贵的那一维
   （每个都是 fd + 一个 ephemeral 端口，星型拓扑下房主要按客人数倍增，100 socket ×
   5 客人 = 500 个 fd，已经逼近 Windows 桌面 1024 的上限），而窗口只花包——包每秒
   都会回补，fd 不会。

   注意 bench 这一节给的是"不限轮数"的命中率，没有建模轮次预算；±220 在极端漂移下
   命中率更高，但走完 441 个目标需要更多轮，12 秒预算内未必跑得完。默认仍是 ±160。

多孔喷射的预算也给了 12 秒：锥型侧要先烧掉自己的单孔预算才开始走窗口，以前两边
共用同一个预算，结果阵列在对端开始走之前就关了。

### 测试方法论：文本断言不算覆盖

v11 修过一个 P0：房间第 5 个及以后的客人，NAT4 打洞每次都抛 `AttributeError`（
`AttemptBudget` 没有 `log` 属性），结果永远走中转。而当时 284 项测试全绿——因为
那条测试是这样写的：

```python
check("no slot -> the attempt is skipped",
      "self.ok = False" in body and "if not self.ok:" in body, ...)
```

它读源码字符串，断言"文件里有 `self.ok = False` 这几个字"。**它证明的只是源码包含
某些字符，从未真正创建一个拿不到 slot 的 `AttemptBudget`。** 一个名为 "no slot"
却从不构造 slot-less 场景的测试，比没有测试更糟——它读起来像是覆盖了。

现在改成真实实例化：开满 `MAX_CONCURRENT_PUNCHES` 个之后再建一个，断言 `ok is False`
、**不抛异常**、且不发包。

同类断言已全部替换为行为验证：**TCP 端口派生**改为直接调用 `_resolve_tcp_port()`（覆盖
30000→30001、65534→65535、65535 不产出 65536、显式覆盖优先）；**端口独占**改为真的二次 bind
并断言抛 `OSError`；**`member_info`** 改为构造真实 `Conn` 后调用 `member_info()` 检查输出；
**filtering 重测**改为运行 `_recheck_nat()` 并计数探测真的被重跑了一次。

### TCP 同时打开需要"端口保留"，否则不该尝试

两端各自 bind 本地端口互拨，而发布给对端的是**本地**端口。所以要成功，两端都必须
**端口保留**（local == public）或有 UPnP 映射——否则拨的是对端 NAT 根本没在监听的端口，
SYN 永远碰不上。

真实日志：对端发布 `tcpPort 30001`，而它的 UDP 30000 映射到 30373——不保留端口。
"did not cross" 是唯一可能的结果，却每轮花 8 秒去证明一次。

**"是否保留端口"必须实测，不能从 UDP 推断。** 曾经的做法是拿 UDP 映射去判：

```
[TCP] skipped: this NAT does not preserve ports (local 30000 maps to public 48520)
      and there is no UPnP mapping, so a simultaneous open cannot cross
```

48520 是 **UDP** 映射。NAT 的 TCP 与 UDP 端口池是**分开分配**的，很多 NAT（含 CGNAT）
一边给 UDP 按目标分配新端口、一边给 TCP 原样返回客户端请求的端口。于是这条判断在最需要
它的网络上、在发出第一个 SYN 之前，就把唯一活着的旁路关掉了。

现在由服务端实测：客户端从打洞端口向服务端发起一条 TCP 连接，服务端回报它看到的源端口。
问到什么是什么，不再推断。旧服务端不支持 `tcp_probe` 时结论为"未测"，此时不禁用该路径，
但只在 UDP 确实无机制时才试（避免每轮白花 8 秒）。

### 入站探测的结论有三种，不是两种

服务端从一个**全新 socket** 发一个 UDP 包给我们——一个我们从没发过 UDP 的主机+端口，
正是打洞开始时对端的样子。收不收得到，是唯一能把"我们扫错了"和"入站被掐了"分开的诊断。

但**收不到 ≠ 被封堵**。曾经的代码就这么认为：

```
[NAT] filtering: endpoint-independent (anything may come in)
[NAT] inbound UDP is BLOCKED: ... at 220.178.180.6:48520 from a fresh source port
      and it never arrived. No amount of punching can help ...
```

真实日志里，**同一对的两端、两个不同 ISP、同一分钟**都报了 BLOCKED，而两端刚刚都测出
过滤行为是 eif。这两句话不可能同时成立——矛盾本身就是信号。

原因是：那个包来自一个我们**从未发过 UDP** 的主机。按地址过滤的 NAT（address-dependent
filtering，"受限锥型"）**按定义**丢弃它。而这类 NAT 恰恰会在我们主动发过包之后接受该主机
的任何端口——而"我们主动发过包的主机"就是对端，打洞一开始它就是这样。

所以收不到只能**排除 eif**，不能排除打洞。三种结论：

| 结论 | 含义 | 动作 |
|---|---|---|
| `open` | 无关的主机也能进来 | 打洞失败就是我们的问题 |
| `punchable` | 无关主机进不来，但我们发过包的主机能进来（adf） | **正常情况**，继续打 |
| `blocked` | 不请自来的包永远进不来（apdf） | UDP 无望，先试 TCP，再中转 |

探测本身也做对了两件事：

- **先朝服务端建映射再探测**（用服务端自带的 STUN 问到"通往服务端的公网端口"，把探测打向
  那个端口）。否则在按地址过滤的 NAT 上，探测包必然被丢，答案永远是"不通"。
- **两种测量不一致时以探测为准**。eif 是 STUN 推断出来的，而服务端可能根本没实现
  CHANGE-REQUEST；探测是"一个包到了 / 没到"的事实。二者冲突时改推断（`effective_filter`）。

### 打洞照抄 OpenP2P：三种握手，四种组合

自研的窗口扫描、步长预测、生日碰撞在这之上全部退为**兜底**。先走 OpenP2P
（`core/holepunch.go` + `core/p2ptunnel.go`），它只有四行调度：

```go
cone x cone        -> handshakeC2C
symmetric x sym    -> ErrorS2S   // 不尝试 UDP 打洞
peer sym, me cone  -> handshakeC2S
peer cone, me sym  -> handshakeS2C
```

两个非对称分支互为镜像，而**分工和我之前写的正好相反**：

| | 谁猜 | 做什么 |
|---|---|---|
| **C2S**（我是锥型） | 我猜 | **一个 socket**（绑在固定打洞端口），朝 800 个随机端口各发一包 |
| **S2C**（我是对称型） | 对端猜 | 开 **800 个 socket**，每个朝**对端那个已知端口**发一包。**一个目标端口，800 个源端口** |

对称型那一侧的职责是**摆出靶子**，不是瞄准。锥型那一侧的端口根本不动，之前让对称侧
去扫它几千个端口，等于对着一个常量做穷举——8100 个包，零回包。

参数也是照抄的（`protocol.go`）：

```go
SymmetricHandshakeNum = 800 // 0.992379
HandshakeTimeout      = 7s
```

一次性发完、等 7 秒，不分轮。命中率是两侧之积：800 个靶子 × 800 次猜测。

**C2S 侧从"发布出去的端口"出发**不是风格问题：按"地址+端口"过滤的对端只接受它发过包的
那个端点，从别的源端口发去的猜测在路由之前就被丢弃。所以 C2S 用 hub socket（固定端口），
并且**接管 hub 的 catch-all**——否则回包到达 hub 时匹配不到隧道，会被当作不可路由丢弃，
喷再多也收不到。OpenP2P 的 `rand.Perm` 不含"对端告诉我们的那个端口"，这里把它放在第一位：
那是唯一确定的地址。

### NAT 判定也照抄：只分锥型/对称型

`nat.go` 全文就一句判据——**同一个本地端口，向同一个 IP 的两个不同端口各发一包**：

```go
natType := NATSymmetric
if port1 == port2 { natType = NATCone }
```

问的是一件事：换目标端口会不会换映射。不会 → 锥型（所有对端看到同一个端点）；
会 → 对称型。**不再细分 sequential / random，不做任何端口预测。**

之前这里在"只有一个 STUN IP"时返回 unknown，理由是两个端口同 IP 无法区分锥型和
"按目标 IP 分配"。理由没错，但 unknown 不是安全选项——OpenP2P 的三种握手**只按
锥型/对称型选择**，unknown 会把三个全关掉，于是只有一个 STUN 端点的服务器后面，
锥型对端彻底没有可用路径。现在同 IP 同端口 → 锥型，不同 → 对称型（步长照旧不发布）。

### 猜对端的端口时，源端口必须是"发布出去的那个"

"发布出去的那个"

这是 cone × symmetric 这一对里**最容易漏、也最致命**的一点。

真实日志，锥形一侧（NAT3）：

```
[NAT] cone (ports [30000, 30000])                 <- 发布端口 30000
[punch] sym_to_cone: 100 sockets, 901 ports, 12s budget
[punch] covered 8043 ports 57493..65535; sent 8100 packets
[punch] no packet from 220.178.180.180 reached any of our mappings.
```

8100 次猜测，**每次一个不同的源端口**（每个 socket 一个）。而按"地址+端口"过滤的
对端（NAT3 正是如此）只接受它**发过包的那个端点**——`(我们的IP, 我们发布的端口)`——
其余全部丢弃。所以这 8100 个包在被路由之前就已经没了，**窗口再宽也没用**。

OpenP2P 的 `handshakeC2S` 正好相反，这也是它对称型策略的全部：

```go
conn, _ := net.ListenUDP("udp", t.localHoleAddr)   // 一个 socket
for i := 0; i < SymmetricHandshakeNum; i++         // 800 次猜测
    UDPWrite(conn, peerIP:randPorts[i]+2, ...)     // 多个目标端口，一个源端口
```

现在：**当本端映射稳定（cone）时，扫描全部从 hub socket 发出**——它的源端口就是发布
出去的那个，也是对端唯一会接受的那个，而且回包也正好落在它上面。对称型一侧没有
"唯一正确的源端口"，仍然用多孔数组。

### 端口窗口会绕回来，不会停在 65535

```
[punch] window exhausted at 19999 ports
[punch] covered 8043 ports 57493..65535 around anchor 57492
```

锚点 57492，往上走只有 8043 个端口就到顶了，walk 把超范围的直接丢掉然后停住。
申请的是 19999，实际覆盖 8043；**锚点下方那 56000 个端口一次都没试过**。

端口空间是环形的。现在 walk 会绕回来（只在近侧全部试完之后，所以不会重复）。这一点
对"判成顺序递增"的对端也值得做：同一台机器测出的步长先是 1，后来是 350，再后来是
760——它的分配器并不是纯 +1。

### 对端按目标 IP 分配端口时，窗口要整个丢掉

参考 OpenP2P：`core/holepunch.go` 对对称型对端**不用窗口**，用的是全域随机排列：

```go
randPorts := r.Perm(65532)                  // 不重复，覆盖整个端口空间
for i := 0; i < SymmetricHandshakeNum; i++  // 800
    UDPWrite(conn, peerIP:randPorts[i]+2, MsgPunchHandshake, ...)
```

`SymmetricHandshakeNum = 800 // 0.992379` 那个 0.99 是**两侧之积**：对称侧开 800
个映射（`handshakeS2C`：800 个系统分配端口的 socket，各发一包后等），对端朝 800
个随机端口喷。不是任何一侧单独的功劳。

真实日志，一台机器：

```
[NAT] sym_easy_inc (ports [47524, 41105], next from a new socket: 47559)
[punch] covered 5500 ports 56720..62317 around anchor 56719
```

三个目标、三个区间——47524 与 41105 来自两个不同的 STUN IP，56719 是它发布的锚点。
窗口绕着 56719 铺 5500 个连续端口，**不可能**包含它为"我们"这个第四个目标分配的
端口。11,055 个包就此作废。

所以现在：一旦测出（或收到）对端按目标 IP 分区，**窗口整个不用**，改全域均匀随机，
并把映射数从 100 提到 800。

### 打洞失败要说清是哪一端的问题

"punch failed" 不可操作，而两种原因的处理方式完全相反：

- **一个包都没收到** → 对端没在打洞（中转模式 / 旧版本 / 没收到 start_punch）。
  洞需要两端都有流量，本机再怎么喷也没用，要去**对端**排查。
- **收到了但没握手成功** → 问题在己方（窗口漂移、过滤行为）。

现在会明确区分这两种。另外首轮失败后会向服务端请求**重新协调**（force），让对端拆掉
已有通道、重新按共享起跑时刻打一次——这是对"对端已转中转不再打洞"这种情况唯一的
自动恢复手段。

### 扫描窗口会向外扩展，而且每轮都是新端口

真实失败案例（cone 侧 ↔ sym_easy_inc 侧，两端都是 eif，理论上必通）：

```
22:41:40 [punch] sym_to_cone: 100 sockets, 161 ports, 12s budget
22:42:14 direct #1 failed: udp punch timeout after 25s (sent 5400 packets to 50 ports)
```

多孔 12 秒 + 单孔 25 秒，全都打不中。两个原因：

**一、每轮是"旋转"而不是"新端口"。** `send_round_robin(ports, offset=rnd)` 让 socket i 打
`ports[(i+R) % len]`，第 R 轮只是整体挪一位。100 socket 配 161 端口，144 轮之后只覆盖
了 **100+144 = 244 个**不同端口——窗口远端永远碰不到，跑多久都没用，加宽窗口也没用。

现在每轮从"没打过的端口"里取一批：900 个端口 **9 轮**全覆盖。

**二、窗口被锚点封顶。** 对端发布映射后要过几秒才开阵列，这期间它机器上每条无关的 UDP
流都把下一次分配往前推。bench 实测 drift=160 时，160 的窗口命中率只有 58%。

现在窗口是**分带、由近及远**的：先打最近的 160 个，没中再向外走到 900。对端几乎没漂移时
第一带就命中，**宽搜索不花额外代价**；漂移很远时也不会束手无策。

**三、锥型侧不该 `send_all`。** 锥型的映射对所有目标都一样，开 100 个 socket 得到的是同一
个端口——"打开更多映射"这件事它做不到。每轮 200 包里有一半（send_all 到对端**连接时**的
端口，而它早就挪走了）是纯浪费。现在锥型侧跳过，预算全部给扫描，**覆盖速率翻倍**。

### 打洞前必须刷新锚点（这是 NAT4 打不通的最大单一原因）

对端扫描的是我们**发布的端口附近**的窗口。而那个端口是**连接时**测的——在一个分配游标
持续移动的 NAT 上，等真正开始打洞时它早就错了。

真实 CGNAT 实测（同一个 socket、同一个内网地址）：

```
23:20:23  radix published 220.178.180.180:22116   delta=1
23:21:53  radix published 220.178.180.180:28745   delta=1
```

90 秒移动 6629 个端口，**约 73 端口/秒**。一次在最后一次发布后 140 秒才开始的打洞，
扫描锚点偏离 socket 阵列实际落点约 **10,000 个端口**——窗口再宽也盖不住这个量级的误差，
所以双方各打几千个包、一个都没收到。

现在在"等待同步起跑"那段空闲时间里重新探测并发布一次端点，让锚点从"几分钟前"变成
"几秒前"。误差从 10,000 降到个位数，被 ±900 的窗口完整覆盖。

### 测量工具必须跟着代码走（不然参数是被"测"错的）

`bench_punch.py` 曾经和两个地方脱节，而两处都让"加宽窗口"看起来有害：

* 扫描在模型里是**旋转**（`ports[(i+r) % len]`），代码早已改成每轮取新端口。
  旋转的覆盖率上限是 `n_sockets + 轮数`，所以加宽列表看起来毫无用处。
* 窗口构造没传代码里的 `max_window`，量的是一个代码已经不执行的扫描。

用真实算法 + 漂移重测（`both_easy`，24 seeds）：

```
sockets/窗口/最大   drift 0   drift 30   drift 60   drift 300
84 / 64  /  -         75%       25%         0%         0%      ← 旧参数
84 / 160 / 900       100%       91%        83%         0%      ← 现在
84 / 64  / 900       100%      100%         4%         0%
```

关键在**第一带必须 ≥ drift + socket 数**：对端的阵列占据从它游标漂移到的位置开始的
连续 N 个分配，第一带窄于这个数就只削到阵列近边，扫得再远也没用。

drift≥300 时任何宽度都是 0%——两端游标在扫描期间都在动。这正是必须在打洞前刷新
锚点的原因，而不是把窗口无限加宽。

### socket 关闭后不要再往里发（日志刷屏）

真实日志里，断开后每秒几百行 `[WinError 10038] 在一个非套接字上尝试了一个操作`，
一直刷到进程退出。原因是 hub 关掉 30000 之后，那些 tunnel 的 keepalive 与重传循环
还在跑——它们不拥有 socket，无从知道它没了。

现在 `UdpHub.close()` 会停掉所有注册过的 tunnel；`_sendto` 在已停止时静默返回，
且同一个错误只报一次（30Hz 重复会把真正的故障埋掉）。

### 一个 IP 的 STUN 应答不能判成 cone（这是最伤的一次误判）

"同一 IP 的两个端口给出同一个映射"既可能是 cone，也可能是**按目标 IP 分配**的 NAT——
只有一个服务器可问时两者无法区分。而公网 STUN 在国内基本不可达，单服务器正是常态。

旧代码返回 cone，**这会关掉整条 NAT4 链路**：

| 环节 | cone 时 |
|---|---|
| `punch_plan` | `METHOD_CONE` |
| `_multi_socket_first()` | `False`（不开阵列、不扫窗口） |
| `_await_punch_start()` | 直接 return，不等同步 |
| `_refresh_anchor_if_stale` | 根本不调用 |
| `_should_scan_window()` | `False` |

最后只剩单孔对着对端**面向 STUN 服务器**的映射打，而按目标过滤的 NAT 一律丢弃。
用户看到的是"连不上"，且没有任何打洞日志。

现在返回 `UNKNOWN`——`_punch_plan_for` 会把 unknown 升级为真实机制，阵列仍会跑；
而 cone 不会。多个不同 IP 都回答时 delta==0 才是真的 cone。

### hard × easy 不该放弃

服务端日志实证：

```
23:24:07  peer A   symmetric/sym_hard
23:24:07  peer B   symmetric/sym_easy_inc
```

命中 `peer_sub == HARD and my_sub in (EASY_INC, EASY_DEC)` → `METHOD_NONE` → 无阵列、
无窗口、不等同步，直接中继，一个包都没发。

但这一对不是无解：easy 侧的端口**可预测**，有窗口可扫；只有 hard 侧猜不到，那只是去掉
一半机制，不是全部。而且 `METHOD_BIRTHDAY` 在这两个分支之后，返回 NONE 连碰撞攻击也否了。

现在只有 **hard×hard 且过滤严格**才放弃；hard×easy 走 `SYM_TO_CONE`，hard×hard 两端 EIF
走 `BIRTHDAY`。

### 扫描不能把 socket 序号和端口序号绑在一起

per-flow NAT 下命中要同时满足"打中了对端的映射"且"该映射记录的 dest == 我的源端口"。
`send_round_robin` 让 socket i 打 port i，两式联立化简为：

```
2r ≡ d_a + d_b   (mod N)
```

`2r` 恒为偶数，所以**漂移和为奇数时数学上无解**——约一半的真实会话在开始前就注定失败，
而且窗口多宽都没用，因为约束的是**轮次 r**而不是 span。

实测（N=100，窗口 900）：

| drift (a,b) | 绑定 | 解绑 |
|---|---|---|
| 0, 0 | 100% | 100% |
| 0, 1 | **0%** | 100% |
| 30, 31 | **0%** | 100% |
| 60, 61 | **0%** | 75% |

现在每轮给每个 socket **随机**分配批次里的端口（`send_scatter`），源端口与目标端口独立，
同余式消失。另外窗口走完不再 `break` 而是回绕——对端游标在扫描期间一直在动，第二遍是
新的观察而不是重复。

顺带否掉了一个建议：socket 数从 100 减到 25。实测 25 个在 drift=30 时是 **0%**（100 个是
100%）——socket 少意味着映射少，也就是**靶子更小**，这个损失比多出来的轮次更贵。

### 窗口不能回绕：跑过的端口已经空了

两端每轮各消耗 `n` 个新映射，所以第 `span/n` 轮之后窗口里每个端口都已被腾空，
重新覆盖它们在数学上不可能命中。实测（n=100, span=900 → 有效 9 轮）：

```
轮次上限   1    3    5    9   15   40  120
命中率   70%  95% 100% 100% 100% 100% 100%
```

第 9 轮之后一个都没多中。v14 的"循环复用"因此是无效改动——12 秒预算里只有约 0.75 秒
在做有效功。

现在改成**由近及远、永不重复**的外扩走法（`_next_ports`）：带内随机、带间有序，
对端几乎没漂移时第一带就命中，宽搜索不花代价；漂移很远时也能一直往外走。

### 生日攻击曾经是死代码

`METHOD_BIRTHDAY` 只在 `my_sub==HARD or peer_sub==HARD` 时产生，而喷随机端口的条件是
`my_sub != HARD`。于是 hard×hard 时**两端都不喷**，攻击从未发生——它只对 cone×hard 生效，
而那是另一个场景。v14 刚为 hard×hard+EIF 打开的这条路，实际是空的。

现在：cone×hard 由 cone 侧喷；**hard×hard 两端都喷**（两端 EIF 时门本来就开着，只差端口）。

### APDF 下"开映射"是无效的，且该立刻中继

`send_all` 写到 `(peer_ip, peer_port)`，这样开的映射只接受来自**该确切地址**的回包，
而对端是从它阵列里的某个端口回的——端口不同，APDF 一律丢弃。所以对端 APDF 时
`send_all` 是每轮一半预算的纯浪费。

这也解释了为什么"先听见再回话"从 v9 建起来却从未在真实日志里生效：30000 的映射是面向
**STUN 服务器**建的，ADF/APDF 都只放行"我写过的主机"，STUN ≠ peer，只有 **EIF** 才收得到。

因此：**APDF + 任一端不可预测 → 直接中继**，不烧两次 12 秒。两端都可预测时 APDF 仍可试
（两端都往对方的真实地址发，回包来源正是写过的地址）。

### bench 第三次给出误导结论的原因

它每轮只推进 1 个端口并循环复用固定窗口，从未建模"每轮推进 n 个映射"，所以测不出
`span/n` 这个上限。现在已修正——每段用完向外延伸而不是回绕。

### 收到 force 后不能再用 force 应答（自激循环）

真机 + 虚拟机跑出来的日志，相隔一秒：

```
08:08:02  A -> punch_target(force)
08:08:03  B <- start_punch(force)
08:08:04  B -> punch_target(force)     ← B 用一个 force 去应答 force
08:08:04  A <- start_punch(force)
```

每一方的应答都会重新触发另一方，于是双方整场都在"拆链路 + 重打"，而不是在打洞。
拆链路本身也不是免费的——它丢掉的正是对方正在用的那条。

现在只有**自己主动切换**时才请求重新协调；应答对方的 force 时静默。

### 每条 peer 只能有一个打洞循环（重建路径绕过了守卫）

模式重建路径直接 `spawn(_direct_loop)`，跳过了 `_start_direct` 的单循环守卫。
同一日志：

```
08:08:03  [punch] both_easy_sym: 100 sockets, 901 ports, 8s budget
08:08:05  [punch] both_easy_sym: 100 sockets, 901 ports, 8s budget
```

两个 100 socket 阵列同时喷，共用一个速率桶，彼此把覆盖砍半。

### 两端公网 IP 相同要明说（hairpin）

真机 + 虚拟机（或同一路由器下的两台机器）共享公网出口。此时打给对端公网端点的包
必须出路由器再折返回来——**hairpinning**，大量家用路由器直接丢弃。

症状具有误导性：日志显示 "no packet from <peer> reached any of our mappings"，读起来
像"对端没在打洞"，实际是每个包都被自家路由器扔了。而且它**无法靠调窗口或 socket 数
解决**，所以值得明确说出来。

现在检测到时会直接提示改用两个独立网络（例如一端开手机热点）。

### 自己没有 IPv6 就不能去连对方的 IPv6（本次"对端没在打洞"的真凶）

真机日志，两端都在 NAT4 但**打洞从未对上**。把两份日志对齐才看清：

```
host  radix   locals = ["172.24.0.107:30000", "172.19.160.1:30000"]   ← 纯 v4
guest test1   locals = ["240e:45a:...:30000", "100.167.x.x", "127.0.0.1"]

host   08:32:14  === direct #1: [240e:45a:...]:30000 (IPv6, no NAT) ===
                 ……此后整场再无打洞日志……
guest  08:32:15  [punch] both_easy_sym: 100 sockets, 901 ports
       08:32:25  no packet from 220.178.180.180 reached any of our mappings
```

host 自己**没有**全球 IPv6，却排在候选首位去连 guest 的 IPv6，然后卡在那里不动；
guest 独自打完了整个窗口。guest 报的 "no packet from peer" 读起来像"对端没在打洞"——
把排查方向整个带偏了。

两处修复：

1. **自己没有全球 v6 就跳过对方的 v6 候选**。对方发布 v6 是关于**它**的证据，不是关于我们的。
2. **试过的 v6 失败后不再回来**。候选列表每轮重读且变化时 `idx` 归零，所以失败的 v6
   每次都回到队首，v4 永远排在它后面。

另外单独给 IPv6 握手加了**墙钟上限**（线程 + join）：日志里那次 v6 停留了 14 秒仍无
"IPv6 failed"——`connect()` 收了 budget 却没遵守，于是调用方也得强制一次。

### 不再把 127.0.0.1 当作 LAN 地址发布

同一份日志里 guest 发布了 `"127.0.0.1:30000"`，来源是 `getaddrinfo(gethostname())`——
很多机器上它解析到回环。发布给全房间成员等于让别人拨自己。已过滤。

### "没收到对端任何包"必须说清是**谁**的问题（真实 NAT4 日志）

两端都是 `sym_easy_inc` + `eif`，同步起跑正常（08:46:19 双双开打），8 秒各扫 100 socket，
然后双方都报 `no packet from <peer> reached any of our mappings`。

旧措辞把两种完全不同的失败都说成"对端没在打洞"——实际上：

* **我们发了上千包、一个都没回来** → 入站方向被过滤/阻断（NAT 或中间 ISP）
* **我们几乎没发包** → 打洞根本没跑，是自己的预算/限速

而且它没说**锚点有多旧**。房主 08:45:29 发布 `43985/43986`，08:46:19 才开阵列——
锚点已经 50 秒；在这个 NAT 上（实测数十端口/秒）意味着整扇窗口偏了数千端口，
再宽也盖不住。

现在失败行会带上：覆盖了多少端口、端口号区间、锚点及其年龄
（`STALE: measured 50s ago`）。下一次日志能直接区分这几种失败。

另外把锚点刷新从"同步等待之后"挪到"之前"：放在后面时，重新测量的值只是在双方
已经按 start_punch 里的旧值开始喷射之后才更新——而对端手里拿的正是那个旧值。

### 窗口锚在"发往 STUN 的端口"，而阵列开在"发往对端的端口"（本次未打通的根因）

真实日志，两端各发一万多包、覆盖五千多个端口，一个都没到：

```
radix  covered 5300 ports 52580..58015 around anchor 52579; sent 10600
test2  covered 5800 ports 44021..49940 around anchor 44020; sent 11600
双方    no packet from <peer> reached any of our mappings
```

扫描锚点是**对端发布给 STUN 服务器的映射**，而打洞需要打中的是**对端发往我们时的映射**。
在按目标分配的 NAT 上这是两个完全无关的序列。同一台机器，相隔三秒：

```
09:01:24  同一 IP 的两个端口 -> 44019, 44020     （差 1）
09:01:27  两个不同的 IP     -> 44020, 7647       （差 -36373）
```

同一个 NAT。把第一行读成"顺序递增、可预测"，就导致整扇窗口对准 44020 附近，
而阵列实际开在另一个区域——**发再多包也不可能有一个到达**。

现在每轮把一部分预算（35%）投到**全端口范围的随机端口**，且从第一轮就开始。
如果对方真是顺序的，窗口仍在最初几轮命中；如果不是，随机那部分是唯一能命中的。
这不是"窗口失败后的兜底"——在按目标分配的 NAT 上窗口从一开始就错了。

同时补上日志：只有单一 IP 的样本时会明确说明"这个步长描述的是通往同一主机的
连续流，不能推广到一个全新的目标地址"。

### 两个自己的 bug

* **锚点时间戳从未设置**：只在地址变化时才赋值，而 hub socket 30000 到 STUN 是一条
  长期流、映射永不变化，于是时间戳永远是 0，日志打出 `anchor is 1789693310s old`
  （裸 epoch），且每次打洞都以为锚点很旧而重跑一次完整探测。
* **刷新被调用了两次**（相隔一秒），因为新增调用点后没删旧的。

### 随机占比是净倒退，改用 EasyTier 的 learn 就近扫

`WINDOW_RANDOM_MIX` 曾设为 0.35。独立复算（150 seeds/组，顺序分配 NAT）：

| 漂移 | 纯向外走 | 35% 随机 |
|---|---|---|
| 0 + 6 端口/轮 | 98% | 77% |
| 30 | 89% | 52% |
| 60 | 79% | 32% |

机制：每轮 100 个槽位里 35 个给了随机端口，向外走的速度从 100 掉到 65 端口/轮，
追不上对端游标。而在它专门想救的按目标 IP 分配场景里，随机只换来 0~1%
（命中要同时满足"打中存活映射"和"该映射的 dest == 我的源端口"，8 秒内联合概率不可达）。

**已设为 0。** 真正有用的是 EasyTier 依赖的那条链——**learn 就近扫**：

一旦真的收到对端一个包，那个源地址就是"适用于我们这个目标"区段里的真实映射，
它旁边的端口就是对端其他 socket 拿到的端口。所以：

* 发布给 STUN 的端口 `44020` 与分配给我们的 `7647` 是两个无关区段 → 预测窗口无效
* 但**听见的**地址是适用区段里的真值 → 它的邻居值得扫

新增 `spray_learned_neighborhood()`：学到地址后用**每个 socket 各扫一个不同的邻端口**
（命中要同时满足两个条件，用满 socket 才能覆盖第二个）。

同时 `send_all` 现在带上 **hub socket**：在按目标 IP 分配的 NAT 上，对端能看到的
区段正是 hub socket 发布端口所在的区段，而 array 的映射在另一个区段，对端无从猜起。

### 单 IP 的样本"诊断了但没治"

日志说了步长无意义，代码却照旧发布 `sym_easy_inc, delta 1`，于是对端围着错区段扫。
现在单一 IP 时直接返回 `UNKNOWN`（`_punch_plan_for` 会升级到多孔，不是降级）。

### unknown 的分配方向要双向走

`_peer_subtype` 对只报 coarse "symmetric" 的老对端默认 `EASY_INC`，若它实际递减则
只向上走必然 0%。旧的 `port_window` 是双向的，新的退化过。现在 unknown 双向。

### bench 加了按目标 IP 分配的模型

| 轮数 | learn 链 | 纯窗口 |
|---|---|---|
| 2 | 100% | **0%** |
| 20 | 100% | **0%** |

窗口在这种 NAT 上**完全无效**——它对准的区域对端从未被分配过。

### 一个包都收不到时，别急着怪防火墙

曾经这里写的是"先查防火墙"，程序还会弹 UAC 去给自己加放行规则。实测证明这是**噪音**：
两端防火墙都明确关掉的情况下，每一份日志照样报"桌面防火墙没有放行规则"，而真正的原因
是扫描的源端口不对（见上）。

一个允许程序**发出**的主机防火墙，同样允许它接收自己发出请求的**回包**——所以它不是
打洞对端的样子。真正会拦下打洞包的是**路由器/NAT 的过滤行为**（apdf），而那是入站
探测该回答的问题，不是本机设置。

所以现在：程序不检测、不修改、不提示任何主机防火墙，也不弹 UAC。

### 入站可达性必须**测**，不能推断（本次新增，最有价值的一条诊断）

"没收到对端任何包"同时出现在两种完全不同的情况里：

* 对端的包在到达之前就被丢弃（ISP / 严格过滤）
* 我们自己的扫描打偏了

两者的应对**相反**——前者不是代码能修的，后者是。而打洞路径里没有任何一行能区分它们。

现在客户端连上后会让**服务端从一个全新的 socket**（一个我们从没通信过的源端口）发一个
UDP 包到我们的映射端口。这正是打洞开始时"对端"的样子。

```
[NAT] inbound UDP works: an unrelated host reached us at 1.2.3.4:44635,
      so a failed punch is ours to fix
```
或
```
[NAT] no unsolicited inbound UDP at 1.2.3.4:44635: filtering is unknown,
      so a host we send to CAN still reach us and the punch is worth
      running. Only apdf would make direct impossible.
```

**这条结果决定下一步该做什么。**

### delta 抖动被当成"网络变化"，静默废掉了退避和黑名单

真实日志，注意前后两个地址完全相同：

```
10:53:56  [NAT] network changed: 220.178.180.180:44635 -> 220.178.180.180:44635
10:53:56  [NAT] cleared direct-connection backoff after the change
```

`delta` 是两个 STUN 服务器看到的端口差，机器上每条无关的 UDP 流都会把它撑大——
同一个会话里实测 1 / 11 / 350 / 760。拿它当"网络变了"，就会每 90 秒触发一次，
于是退避计数永不累积、黑名单永不生效，本该停 12 秒的对端被无限重试。

现在 `nat_changed` 只比较**地址和类型**，step 仍然发布（对端用它预测），但不再是"我们移动了"的证据。

### 锚点年龄打印的是错的时钟

扫描围绕的是**对端发布**的端口，而日志里的 "STALE: measured 34s ago" 用的是
**我们自己上次发布**的时间——两个不相干的时钟。现在改用收到 `start_punch` 的时间。

### "入站被阻断"不能再误报（服务端没升级时它会误报）

两份真实日志，同一分钟，两台机器，两个不同运营商：

```
radix  [NAT] inbound UDP is BLOCKED: ... at 220.178.180.180:12322
0721   [NAT] inbound UDP is BLOCKED: ... at 39.144.154.160:12726
```

两台机器、两个 ISP 同时阻断入站——这个巧合的概率，远低于"服务端是旧版本、
根本不认识 `inbound_probe` 这个 action"。旧服务端静默忽略未知 action，客户端
等 4 秒没收到包，就报 BLOCKED。

**把"我们自己的服务端没升级"说成"用户的网络有问题"，比什么都不说更糟。**

现在服务端发完探测包后会回一条 `inbound_probe_sent` 确认。客户端只有**确认已发送**
且仍未收到，才判定 BLOCKED；收不到确认就报 `inbound probe inconclusive`。

顺带：一旦真的确认阻断，AUTO 模式**直接转中继**，不再每 33 秒喷 12 秒证明同一件事。

### 锚点年龄的单位错了（epoch 减 uptime）

```
[punch] sent 9090 packets to 12726 (anchor STALE: measured 1789726890s ago)
```

`_punch_recv_at` 存的是 `time.monotonic()`，而算 age 用了 `time.time()`。
两者相减就是 epoch。这行是"锚点还是扫描有问题"的唯一依据，错的单位比没有数字更糟。

### 一个永不返回的候选，会把后面所有候选永久挡住（本次根因）

真实日志，radix 侧：

```
19:04:18  === direct #1: [2409:8924:...]:30000 (IPv6, no NAT) ===
          ……之后 51 秒，再无任何打洞日志……
```

而 IPv4 公网地址排在候选列表**最后**——它一次都没被尝试。

循环每轮只处理**一个**候选，所以任何一次尝试不返回，整轮就停在那里。
IPv6 无 NAT，本该"秒通或不通"，但 `connect()` 跑到 deadline 后**照常返回一个
从未连接的 tunnel**，调用方把它当成可用链路装上，于是：

* 卡住的候选永不释放
* 后面的 IPv4 永不轮到
* 日志只有一行，看不出卡在哪

两处修复：

1. **`_try_ipv6` 只在真正 `connected` 时才返回 tunnel**。跑到超时没连上就是失败，
   并说明"家用路由器普遍允许 IPv6 出、阻断 IPv6 入"。
2. **给"一轮"加墙钟**（`ROUND_WALL_CLOCK_S=30`）。单个候选的超时不够——需要有人
   发现整轮停止推进。超时后丢弃卡住的候选**及其同类**（同一台机器的两个 IPv6 地址
   通常是稳定地址 + 临时地址，只丢第一个会原样再卡一次）。

另外修了一个测试污染：某测试把 `socket.socket` "恢复"成它自己（`_c.socket.socket =
_c.socket.socket`），实际什么都没恢复，后面每个测试拿到的都是假 socket。

### RFC 5780：NAT 有两个轴，之前只测了一个

前面所有关于 NAT 类型的讨论其实只覆盖了一个轴：**映射**（mapping）——出站的流被
分配哪个公网端口。另一个轴是**过滤**（filtering）——什么样的入站包能通过。两者
互相独立：一个 NAT 完全可以"每个目标分配一个新端口"（对称），同时"接受任何来源
的入站包"（endpoint-independent filtering）。

第二个轴靠 RFC 5780 的 `CHANGE-REQUEST` 测量：要求服务器从**另一个 IP/端口**回
应答。如果那个应答能到，说明 NAT 放行了来自我们从未联系过的地址的包。

三个测试：

| 测试 | 请求 | 应答到达意味着 |
|---|---|---|
| I | 普通 binding | 服务器可达 |
| II | 换 IP **且**换端口 | 任意主机的包都能进（`eif`） |
| III | 只换端口 | 我们联系过的主机的包能进（`adf`） |
| — | II、III 都不到 | 只有我们发过的确切地址能进（`apdf`） |

**为什么要多花这三个包**：它决定"谁先开口"。按目标过滤的 NAT 会丢弃对端的包，
直到我们自己先往那个地址发过。如果两端都是这样、都在等对方，就一个包都到不了——
不是洞打不通，是没人去开门。现在 `must_open_first()` 让**更严格的那一端先发**，
而不是靠 node id 抛硬币。

这个轴还修正了一个过度保守的判断：对称映射 + 两端 `eif` 其实是**可打的**（门本来
就开着，只需要猜对端口），而之前映射判定为 hard-symmetric 就直接 `METHOD_NONE`
放弃了。现在只有两端都是 `eif` 才放宽，一端严格就不放——避免把放弃的门槛降得
太松。

一个实现上的坑：STUN 响应里的属性顺序是任意的，而原来的解析器一读到
`XOR-MAPPED-ADDRESS` 就 `return`，排在它后面的 `RESPONSE-ORIGIN` **永远读不到**。
而 `RESPONSE-ORIGIN` 是区分"服务器真的换了地址"和"服务器忽略了 CHANGE-REQUEST"
的唯一依据——后者是大多数公共 STUN 服务器的行为，读不到就会把每个这样的服务器
误判成宽松 NAT。现在会扫完全部属性再返回。

服务器不支持 RFC 5780 时返回 `unknown`，而 `unknown` 的严格度排序**刻意放在中间**
而不是最严：未知是常态，判成最严会放弃掉本来能连通的网络；判松一点的最坏结果
只是乐观。

## NAT 类型周期重判

NAT 类型**不是常量**。路由器重新拨号、笔记本换 Wi-Fi、CGNAT 重新分配端口，都会改变
我们的公网端点或分配行为。而连接时测一次的结果只描述当时的网络——之后它不只是过时，
而是**主动误导**：我们继续朝一个已经不存在的地址打洞，还继续用为那个 NAT 选的策略。

现在每 90 秒重测一次（`NAT_RECHECK_S`），检测到变化就重新发布地址并清掉直连的退避
与黑名单。

**p1 与 p2 的间隔不能用来判"随机"。** 这是从真实日志里抓到的最严重一处误判：

```
18:21  sym_easy_inc   ports [60225, 60226]   next 60227   步长 +1
18:29  sym_hard       ports [60225, 60392]   next 60393   步长 +1
```

第三次探测始终测出 +1，**NAT 根本没变**，但判定从"可预测"翻成了"随机"。原因是旧代码先
检查 `|p2 - p1| > 128` 并直接返回 `sym_hard`，p3 的证据永远没被看到。

而 p1、p2 是**两个不同目标**的映射，它们的差 = 真实步长 + 这期间机器开的无关流数量，
与"是否可预测"无关。能测步长的只有 p3（拿新 socket 问已达服务器，两次分配是连续的）。

现在 p3 优先判定；只有 p3 完全没拿到（探测失败）才退回去看间隔，且这时**乐观**——把随机
判成可预测只浪费一次重试，反过来会永久丢掉直连。

**降级必须被确认两次，升级立即采信。** 实测过一个真实现象：连接时判 `sym_easy_inc`
（可预测），几分钟后房间列表变成"随机"——而网络根本没变。原因是重判每 90 秒跑一次，
通常正好在游戏运行中；它量的是"下一个端口落在哪"，而机器上每一条无关的 UDP 流都会
把答案推歪。撞上两三条，一个顺序分配的 NAT 就读起来像随机。

两种误判的代价不对称：

- 判"可预测"但实际随机 → 打洞失败一次、退避重试、最终中转（**能恢复**）
- 判"随机"但实际可预测 → `punch_plan` 对 hard×hard 直接放弃（**永久失去直连**）

所以好消息立刻采信，坏消息要两次重判都这么说。同时后台重判的采样数从 2 提到 4——
它不阻塞任何人，多花的时间换来的是"最小间隔"更可能逼近真实步长。

端点（地址/端口）变化不受此限：那是事实，不是推断，即使类型降级待确认也会立即发布。

**清黑名单这一条最容易漏**：对旧地址记下的失败，对新地址毫无意义，而黑名单一压就是
几十秒什么都不做。不清就等于在一个本来能直连的新网络上继续走中转。

两个刻意的约束：

- **打洞进行中跳过本轮**。探测必须用同一个 socket（对称 NAT 上从别的 socket 学到的
  映射没有价值），而在打洞中途抢走 hub 的注意力，很可能正好丢掉我们在等的那个包。
  错过一轮 90 秒的检查没有代价，打扰一次打洞可能丢掉整条连接。
- **首次测量缺失不算变化**。启动时没有可比对象，若算作变化就会让第一次重判无条件
  重发、并清掉一份从未挣得的退避。

## TCP 同时打开（TCP simultaneous open）

UDP 打洞是第一选择，但它不是总有：有些网络/防火墙几乎完全封掉 UDP 却放行 TCP，那种
环境下只能中转。TCP 同时打开是一条**真正不同的路径**，不是 UDP 技巧的变体。

做法：两端绑定到**各自固定的本地端口**同时互拨，两个 SYN 在中间交叉，双方内核各自
完成握手。不需要 listen，也不需要服务器。

单 socket 就够了，这是关键：socket 绑定在对端瞄准的端口上，对端的 SYN 到达时，内核
发现该端口上有一个处于 SYN-SENT 的 socket，收到的是 SYN 而不是预期的 SYN-ACK，于是
转入 SYN-RECEIVED 并回应——这就是 TCP 状态机本身的同时打开。

几个实现细节，都是踩过的：

- **一轮之内：一次 connect，然后等满这一轮**。内核会自动重传 SYN，所以不需要拆掉
  socket 重拨；而中途拆掉反而有害——空隙里本地端口上没有 socket，对端交叉过来的 SYN
  会吃到 RST，它的尝试立刻失败。
- **跨轮重拨是必要的**，因为一轮只会在**确定失败**后结束。最常见的是 ECONNREFUSED：
  对端还没 bind 时 SYN 会收到 RST，而 RST 是终态，内核不会在此之后重传。所以每轮最多
  分到 `timeout/rounds` 的预算（不是整个预算），失败后带抖动重来。抖动是必须的，否则
  两端可能同步重试、一直错过。

**一个诚实的限制**：同时打开需要两端都处于 SYN-SENT，而仅仅 bind 了还没 connect 的
socket 收到 SYN 会回 RST。真实链路里 NAT 会吃掉先到的 SYN，重传时再交叉；**回环上没
有东西吃掉它**。实测：40 次带屏障同步的尝试，0 次交叉。所以 `test_nat.py` 第 50 节测的是
分帧与双向收发（用真实 accepted 连接，确定可测），交叉机制本身需要在真实局域网里验证。
- **可写 ≠ 已连接**。非阻塞 connect 后必须读 `SO_ERROR`，只看 select 可写会得到一个
  "能用"的 socket，然后在第一次写入时炸掉。
- **自己分帧**。TCP 是字节流，没有边界；上面 channel 的解析器要的是整帧，所以加了
  4 字节长度前缀。
- **不重复可靠传输**。TCP 已经提供顺序、重传和丢包检测，再在上面实现序号和 ACK 只会
  增加延迟和 bug。
- **固定端口**用 `TCP_PUNCH_PORT=30001`，与 UDP 打洞端口分开，避免两个 bind 抢同一个
  端口，也避免路由上转发其中一个时悄悄影响另一个。

接入位置：第一轮完整 UDP 尝试失败后、彻底放弃之前，**只试一次**。它是另一条路而不是
同一条路的加强版，要么交叉成功要么不成功；每轮都重试等于把整个预算花在第二次
UDP 形态的尝试上。`DISABLE_TCP_PUNCH=1` 可关闭（外向 SYN 突发在部分网络会被当成扫描）。

## NAT 穿透（对称型 / NAT4）

直连按以下顺序尝试，全部失败才走中转：

```
LAN 直连  ->  公网 UDP 打洞  ->  中转
```

**1. 多候选地址。** 客户端同时上报局域网端点和公网端点，服务端交换全部候选。
同局域网的两人不再绕公网一圈（需要路由器支持 hairpin，很多路由器不支持）。

**2. NAT 类型检测。** 用**打洞用的那个 socket** 向两个不同 STUN 服务器各发一次请求：
端口相同 = 锥型，端口不同 = 对称型，差值就是端口分配步长。
（必须用同一个 socket——对称型 NAT 对每个目标分配不同映射，换个 socket 探到的端口毫无意义。）

**3. 对称型 NAT 端口预测（关键）。** 对称型 NAT 对每个目标分配一个全新端口，
所以对方从 STUN 学到的端口并不是它实际用来通信的端口，**只往那一个端口发永远打不通**——
这正是以前 NAT4 下直连失败的原因。

多数这类 NAT 是**顺序分配**端口的，所以真实端口就在已发布端口附近一个小的偏移量内。
我们向 `端口, 端口±Δ, 端口±2Δ…` 喷一小批 HELLO（上限 12 个，避免变成 DoS），
只要有一个落在对方 NAT 实际创建的映射上，洞就打开了。双方同时喷，命中率更高。

EasyTier / Astral 能在 NAT4 下直连，靠的就是同一套思路（`disable_sym_hole_punching` 关掉的就是它）。

**NAT 类型仅供参考，绝不用来判定"无法直连"**——很多 NAT 会误报，唯一可靠的结论是实际打一次。

日志会明确显示当前在做什么：

```
[NAT] symmetric (NAT4): port step=7, punch will predict ports
=== direct #1: 1.2.3.4:5000 (public, 12 port(s)) ===
[NAT] refreshed endpoint 1.2.3.4:5007
```

|---|---|

| `direct` | 只走 UDP 打洞，一直重试 |
| `relay` | 游戏数据经信令服务器转发，只要能连上服务器必定可用 |

**TURN 已移除**——`turn.py`、`deploy-coturn.sh`、`turn-probe.py` 全部删除，

## 四种连接模式

界面上 `mode` 下拉框选择，会自动记忆。

| 模式 | 行为 | 什么时候用 |
|---|---|---|
| `auto` | UDP 打洞，失败 2 次后转服务器中继 | 默认 |

## 架构：每个 peer 一条独立通道

（借鉴了多隧道中继客户端的做法）

每个远端 peer 拥有独立的 `PeerChannel`：**自己的传输、自己的入站队列**，
房主侧还有**自己到本地 MC 的一条独立 TCP 连接**。

为什么必须隔离：如果两个玩家共用一条到 MC 的连接，两人的 MC 协议数据
会被拼进同一个 socket，两个会话同时损坏。

```
房主                                    本地 MC 25565
 ├─ PeerChannel(玩家A) ──> 独立 TCP 连接 ──┐
 └─ PeerChannel(玩家B) ──> 独立 TCP 连接 ──┤
                                          └─> MC 服务端（各自一个连接）
```

配套的三个细节：

- **TCP_NODELAY + 64KB 缓冲**：MC 移动/方块更新都是几十字节的小包，
  不开 NODELAY 会被 Nagle 算法攒包，每次操作多一个 RTT
- **单一 UDP 套接字归 hub 独占读取**：30000 端口只有一个读者按源地址
  分发。多个隧道各自 `recvfrom` 会互相偷包，谁也握不上手
- **入站队列先缓冲、MC 连上再泵**：效果等同于先 READY 再传数据，
  开局不会丢包

代理端口 25566 被占用时会自动向下扫描（25567、25568…），并在状态栏显示
实际端口——同机多开或端口冲突时不会直接失败。

**已知限制**：直连模式下，若两个 peer 位于同一 NAT 之后（公网 IP 相同），
hub 无法区分来源会丢弃该包。这种情况请改用 `relay` 模式。

## 为什么直连改成了 UDP

之前那版 TCP 打洞失败，原因是**写法**，不是协议：

```python
s = socket(); s.connect(peer)     # 没有绑定本地端口
```

TCP 打洞要成立，外连的 SYN 必须**从打洞端口 30000 发出**。
NAT 只在"有包从某个本地端口发出去"时才建映射，而监听 socket 不发任何包，
所以 NAT 上没有 30000 的 TCP 映射，对端发来的 SYN 直接被丢。

另外 NAT 上 UDP 和 TCP 的映射是各自独立的 —— 发 UDP 包不会顺带打开 TCP 的洞。

需要更正以前的一个说法：本节原标题是"TCP 打洞不可能成功"，这个结论下得
太满。绑定本地端口之后 TCP simultaneous open 是可行的，而且**很多 NAT 的 TCP
端口分配比 UDP 更好预测**，在 NAT4 下常常是唯一能通的路（EasyTier 就有独立的
`tcp_hole_punch.rs`）。本版仍未实现它 —— 见"仍未解决"。

现在按 openP2P / ZeroTier / WireGuard 的做法：

1. **只用 UDP** —— 双方同时向对端发包，两边 NAT 各自建映射，洞因此打开
2. **5 秒 keepalive** —— NAT 映射空闲几十秒就失效，不保活洞会自己关上
3. **可靠性自己实现** —— 序号 + 累积确认 + NAK 补洞 + 超时重传 + 乱序重组
4. **在途量受拥塞窗口限制** —— 起始 8 个包，收到 ACK 线性增长、丢包减半
   （上限 64）。窗口是真实门限而不是注释：第一批就打 64 个包进一条没测过
   的链路，在上行小的网络上等于一次性全丢。
   注意"等窗口"和"链路卡死"用的是**两个不同的超时**（3 秒 / 0.25 秒）——
   丢一个包会把累积确认压住整整一个重传周期，健康链路在窗口小的时候
   本来就会"窗口满"几百毫秒，按 0.25 秒放弃等于把普通丢包变成真丢数据。

## 排查

**先切 `relay` 模式。** 能联机说明整条链路（本地代理、转发、MC 端口）都对；
不通的话问题在信令服务器或地址填写。

常见现象：

| 现象 | 原因 |
|---|---|
| 一直 `still punching` | 扫描没打到对端的映射上，或 NAT 过滤太严（apdf）；看 `[punch]` 那几行的覆盖数与源端口 |
| `waiting for MC server on 25565` | 房主还没开 MC 世界（程序会每 2 秒重试，不用管） |
| `port 25566 busy` | 上次没退干净，或别的程序占了 25566 |
| 房间列表空 | 信令地址填错，或安全组没放行 |
| 地址显示 `192.168.x.x` | STUN 失败，在"public IP"里手动填公网 IP |

然后房主 Create、客人 Refresh + Join。

### 多开 Minecraft

**房主**：开世界并对外暴露在 25565（独立服务端 jar 默认就是；
若用「对局域网开放」随机端口，把客户端的 `MC port` 改成那个数字）。
房主自己也用 MC 客户端连 `localhost:25565`。

**客人**：每个客人窗口的日志里会打印
`proxy ready - MC connect 127.0.0.1:25566`，
每个 MC 客户端连**自己那个**端口：

| MC 实例 | 连 |
|---|---|
| guest1 | `localhost:25566` |
| guest2 | `localhost:25567` |
| guest3 | `localhost:25568` |

端口被占会自动往上找，所以**每次都以日志里打印的为准**。
多实例可以用 Prism/HMCL 启动器建多个游戏目录，或直接复制 `.minecraft`。

### 单机端口怎么错开的

| 端口 | 冲突处理 |
|---|---|
| 30000 UDP | 只有第一个客户端能绑定，其余自动随机端口（不影响互相发现） |
| 25566 代理 | 自动顺延到 25567、25568… |
| 设置/设备 ID | 每个实例独立目录 `.localtest/<名字>/` |

### 排错

```bash

```

`local_test.py` 每次启动会自动跑一遍，有问题在开始前就报出来，
不会等你点了 Connect 才崩。

### 谁建房间

**建房的那个窗口 = 连本地 MC 25565 的那个**。它负责把玩家数据喂进本地世界，
其余窗口各自起代理端口。所有窗口都在同一台机器上，所以哪个建都行；
但如果你之后换到真·多机，建房的那台必须跑着 MC 世界。

### 每条 MC 连接都有独立的后端连接

真实 MC 客户端连服务器会开**多条**连接：服务器列表探测（取 MOTD）、真正进服、
重连……而 **MC 服务端在回答完状态查询后会主动关闭 socket**。

如果这些连接共用房主侧那一条到本地 MC 的 TCP 连接，探测一走整条就被关掉，
后续进服无处可去——表现就是"25566 连不上"。

现在 peer 链路上跑的是**流复用**：每条 MC 连接一个 stream id，
房主为每条流单独 `connect()` 一次本地 MC。跟 BungeeCord 这类代理的做法一致。

```
MC 客户端 ──> 客人代理 25566 ──┐
                              ├─ stream 1 ──> 房主:25565 (连接 A)
MC 客户端 ──> 客人代理 25566 ──┘
                              └─ stream 2 ──> 房主:25565 (连接 B)
```

流的管理用带目标 peer 的控制消息（服务端只做转发），
即使控制消息丢了，收到数据也会按需建流。

### 延迟显示 0 ms

早期版本 `_ping_loop` 发了 ping，收到 pong 却直接丢弃——既没算 RTT，
也没上报给服务端，所以成员列表里的延迟永远是初始值 0。

现在 ping 带序号，pong 回来算 RTT（指数滑动平均），变化超过 1 ms 才上报，
避免每几秒就给全房间刷一次 `room_update`。采样间隔 4 秒。

状态栏按延迟着色：< 80 ms 绿，< 200 ms 黄，再高红色。
亚毫秒（本机回环）会上报 1 而非 0，否则和"尚未测量"无法区分。

### 三个端口都是可配置的

| 字段 | 默认 | 含义 |
|---|---|---|
| MC 端口 | 25565 | **房主**本地世界端口 |
| UDP 打洞 | 30000 | 本客户端打洞用，同机多开要改 |
| 本地代理 | 25566 | **房客**的 Minecraft 要连的端口 |

三个都在界面「身份与本地端口」里，会自动保存。端口被占用时自动顺延，
日志会打印实际用的那个——**以日志为准**。

### 已知坑：第二台设备一登录，第一台就掉线

根因是 `.device_id` 是文件里存的一串随机 UUID。把程序文件夹复制到另一台机器
（或打进 exe 分发），两台机器的 id 就完全相同，服务端把第二次登录当成"同一设备
重连"，于是主动踢掉第一条连接。

现在 device id 绑定了**机器指纹**（主机名 + MAC）：

```
.device_id 内容:  <uuid> <机器指纹>
```

启动时校验指纹，不符就说明文件是从别处复制来的，自动重新生成。
（`test_e2e.py` 第 10 节守着这个行为。）

万一还遇到，删掉该文件重启客户端即可。

### 已知坑：MC 的"服务器列表探测"

真实 MC 客户端连服务器会开**两条**连接：

1. 服务器列表探测 —— 连上、取 MOTD、**立刻断开**（只为渲染列表那一行）
2. 真正进服 —— 再开一条新连接

早期版本里探测那条连接一断开就会连带关掉整条 peer 通道，
于是第 2 步进来发现通道已死，直接被重置——表现就是 25566/25567 连不上。
现在每条 MC 连接用独立的停止信号，探测不再影响后续进服。
（`test_e2e.py` 第 7 节专门守着这个行为。）

### 大包：为什么帧要带长度

MC 单包能到几十 KB（区块数据）。UDP 隧道 MTU 是 1300，**一个逻辑消息会被拆成
几十个分片逐个交付**——只有第一个分片带流头，其余的会因为没有头部而落到错误的流上，
数据被撕开送到不同的后端连接。

所以帧格式是 `[0x02][stream_id:4][length:4][payload]`，接收侧缓冲到声明长度齐了才吐出。
这样无论传输层是一次给完（WebSocket）还是切成几十片（UDP 隧道）都能正确重组。

（`test_e2e.py` 第 10 节用 60KB 实测两条路。）

### 拓扑是星型的

服务器只让**客人和房主**配对，客人之间不建连。之前两两配对时，
客人会多出一条通往另一个客人的通道，导致它的本地代理可能挑错通道——
单机 3 人测试直接暴露了这个问题。
